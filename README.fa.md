# 🛡️ aestun — تانل رمزنگاری‌شده و ضد DPI بین دو سرور

> `🐧 لینوکس` · `🔒 AES-256-GCM / ChaCha20-Poly1305` · `🥷 استتار QUIC، TLS و DTLS` · `📦 یک باینری استاتیک` · `🛰️ ناظر DPI داخلی` · `⚙️ مسیر بسته بدون allocation`

**English version: [README.md](README.md)**

یک تانل کوچک و سریع بین دو سرور اوبونتو (ساخته‌شده برای لینک **🇮🇷 ایران ↔ 🌍 خارج**). ترافیک IP
را روی یک اینترفیس TUN با IPهای خصوصی جابه‌جا می‌کند، هر بسته را با **AES-256-GCM** (یا
**ChaCha20-Poly1305** روی CPU بدون AES-NI — بخش ۷) رمز می‌کند، و طوری طراحی شده که ترافیک روی
سیم **از دادهٔ تصادفی قابل تشخیص نباشد**: بدون handshake، بدون هدر ثابت، بدون امضای پروتکلی.
علاوه بر این خودش **DPI را رصد می‌کند** و ثبت می‌کند چه کسی پورت را پروب می‌کند و شبکه چه بلایی
سر بسته‌ها می‌آورد (بخش ۱۰).

با Go نوشته شده و وابستگی‌هایش vendor شده‌اند، پس **آفلاین هم** به یک باینری استاتیک بدون
وابستگی build می‌شود.

## 🧭 ۰. از اینجا شروع کنید

### این پروژه چیست؟

دو سرور، و یک تانل رمزنگاری‌شده بین‌شان. نتیجه یک لینک شبکهٔ خصوصی است
(`10.8.0.1` ↔ `10.8.0.2`) که هر ترافیک IP را جابه‌جا می‌کند، و بایت‌هایی که روی سیم می‌روند
طوری ساخته شده‌اند که دستگاه **DPI** نتواند تشخیص دهد چه هستند.

### معماری معمول

<div dir="ltr">

```
   کاربران شما  ──▶  🇮🇷 سرور A  ══ تانل رمزنگاری‌شده ══▶  🌍 سرور B  ──▶  اینترنت
                     (role "a")        شبیه QUIC             (role "b")
```

</div>

یک سرور داخل شبکهٔ سانسورشده، یک سرور خارج. کاربران به سرور داخلی وصل می‌شوند و ترافیک‌شان
از داخل تانل بیرون می‌رود.

### نصب

روی **هر دو سرور**:

<div dir="ltr">

```bash
git clone https://github.com/3aeidkhalili/AES-256-GCM-anti-DPI && cd AES-256-GCM-anti-DPI
sudo ./aestun.sh install
```

</div>

بعد از نصب، `sudo ./aestun.sh` منوی مدیریت را باز می‌کند.

> ⚠️ سه چیز **باید روی هر دو سرور دقیقاً یکسان باشد**: `key`، `cipher`، و `obfs`.
> `role` باید **متفاوت** باشد (یکی `a`، دیگری `b`). بقیه برای هر سرور جداست.

### کدام گزینه‌ها را انتخاب کنم؟

| سؤال | پاسخ | چرا |
|---|---|---|
| `transport` | **`udp`** | حدود ۳ برابر سریع‌تر از `tcp` (۶۵۰ در برابر ۲۰۰ مگابیت) و پینگ به‌مراتب بهتر. `tcp` فقط وقتی UDP کاملاً بسته باشد. |
| `obfs` | **`quic2`** | ترافیک را شبیه یک اتصال عادی QUIC می‌کند. `quic` ظاهراً همان است ولی بستهٔ آغازینش **در شبکه‌های ایران حذف می‌شود** (§۴٫۳). |
| `cipher` | **`chacha20-poly1305`** مگر اینکه *هر دو* CPU از AES-NI پشتیبانی کنند | روی CPU بدون AES-NI، AES نرم‌افزاری و کند است (§۷). |
| بافر سوکت | **۲ مگابایت** (پیش‌فرض) | بزرگ‌تر بهتر **نیست** — بافر یک صف است (§۶). |
| ماژول‌های ضد DPI | اول همه **خاموش** | فقط اگر لینک واقعاً دچار اختلال است روشن کنید (§۹). |

### مطمئن نیستید کار می‌کند؟

`sudo ./aestun.sh` → گزینهٔ **۴) تست اتصال**. اگر پینگ رد شد، تانل بالاست. اگر نه → §۱۳.

### واژه‌نامه

| اصطلاح | به زبان ساده |
|---|---|
| **DPI** | دستگاه سانسورچی که ترافیک عبوری را می‌خواند و تصمیم می‌گیرد چه چیزی را ببندد. |
| **carrier** (حامل) | اتصال واقعی UDP/TCP بین دو سرور شما، که همه چیز داخلش پنهان می‌شود. |
| **obfs / استتار** | این‌که حامل را *شبیه* یک پروتکل معمولی نشان دهیم تا DPI کاری به آن نداشته باشد. |
| **cover** (پوشش) | بسته‌های آغازین ساختگی که نشان می‌دهند یک نشست واقعی QUIC یا DTLS شروع شده. هیچ داده‌ای حمل نمی‌کنند. |
| **role a / role b** | کدام سر کدام است. `a` گفت‌وگو را شروع می‌کند (روی سرور داخل)، `b` جواب می‌دهد. |
| **bufferbloat** | صف‌های بیش‌ازحد بزرگ. سرعت خوب است ولی به‌محض شلوغ شدن لینک پینگ خراب می‌شود. |
| **AEAD** | رمزنگاری که هم‌زمان محرمانگی و اصالت را تضمین می‌کند. |
| **MTU** | بزرگ‌ترین اندازهٔ بسته‌ای که مسیر بدون تکه‌تکه شدن عبور می‌دهد. |

## 🔐 ۲. چطور کار می‌کند

هر بستهٔ IP که وارد `tun0` می‌شود:

۱. یک شمارندهٔ ترتیب ۸ بایتی (ضد replay) و طول padding به ابتدایش اضافه می‌شود — **داخل**
   رمزنگاری، پس روی سیم دیده نمی‌شود.
۲. با **AEAD** رمز می‌شود (AES-256-GCM یا ChaCha20-Poly1305)، با کلید مستقل برای هر جهت.
۳. یک هدر ۱۳ بایتی می‌گیرد که **هم‌زمان nonce رمزنگاری هم هست** — بسته به حالت استتار،
   یا هدر کوتاه QUIC است یا رکورد DTLS. (با `obfs: none` این هدر یک nonce تصادفی ۱۲ بایتی است.)
۴. از UDP (یا TCP) به سرور مقابل می‌رود.

**چرخش کلید:** کلیدها بر اساس زمان و **بدون هیچ تبادلی** هر ساعت عوض می‌شوند
(`rekey_interval`). چون هر دو سر ساعت دارند و کلید مشترک، نیازی به پیام هماهنگی نیست — و
همین یعنی هیچ handshake ای روی سیم وجود ندارد که DPI بتواند رویش امضا بسازد.

**ضد replay:** پنجرهٔ ۴۰۹۶ تایی روی شمارندهٔ ترتیب. بستهٔ تکراری یا خیلی قدیمی دور ریخته
می‌شود و در آمار به‌عنوان `replay_drop` شمرده می‌شود.

**عملکرد:** مسیر بسته هیچ allocation ای ندارد — ساختارهای کاری بین بسته‌ها بازاستفاده
می‌شوند، AEADها از طریق atomic بدون قفل خوانده می‌شوند، و تصادفی از یک CSPRNG بافرشده
می‌آید نه یک syscall به‌ازای هر بسته.

## 🥷 ۴. استتار: کدام حالت `obfs`؟

مهم‌ترین بخش این سند.

محتوای بسته‌ها رمزنگاری‌شده است، پس در برابر بازرسی *محتوا* چیزی برای بهتر کردن نمانده —
بایت تصادفی یکنواخت بهینه است. مشکل این است که **همین خودش نشانه است**: هیچ پروتکل واقعی‌ای
از بایت اول کاملاً تصادفی نیست، اندازهٔ بسته‌هایش دوقله‌ای نیست، و keepalive اش دقیقاً
ساعت‌وار نیست. لایهٔ استتار به این سه نشانه حمله می‌کند، نه به رمزنگاری.

| نشانه | کاری که این لایه می‌کند |
|---|---|
| آنتروپی بالا از بایت صفر | هدر کوتاه QUIC — بیت فرم، بیت ثابت، connection ID پایدار |
| شمارندهٔ آشکارا صعودی | شماره‌های بسته دقیقاً مثل RFC 9001 محافظت می‌شوند، پس فیلد تصادفی به نظر می‌رسد |
| هیچ handshake ای دیده نشده | جریان با یک بستهٔ Initial واقعی حاوی ClientHello (با SNI و ALPN=h3) باز می‌شود |
| بسته‌های داده بی‌ربط به آن handshake | هر سر، connection ID ای را که طرف مقابل اعلام کرده می‌پذیرد |
| اندازه‌های دوقله‌ای | اندازه‌ها روی سطل‌ها گرد می‌شوند |
| keepalive دقیقاً دوره‌ای | بازه ±۴۰٪ jitter می‌گیرد |

### ۴٫۱ چهار حالت

| حالت | چه شکلی می‌شود | کِی |
|---|---|---|
| `none` | بایت تصادفی خام | فقط سازگاری با نسخه‌های قدیمی؛ **کندترین گزینهٔ UDP هم هست** |
| `quic` | QUIC نسخه ۱ | روی شبکه‌های ایران پوشش آغازینش حذف می‌شود — §۴٫۳ |
| `quic2` | QUIC نسخه ۲ (RFC 9369) | ✅ **پیش‌فرض توصیه‌شده** |
| `dtls` | رکوردهای DTLS 1.2 | وقتی خودِ QUIC مشکوک یا بسته باشد |

### ۴٫۲ روی TCP، استتار **TLS** است نه QUIC

QUIC یک پروتکل UDP است، پس روی حامل TCP شکل درست، TLS است. با
`transport: tcp` + `obfs: quic` (یا `quic2`):

* اتصال با یک **handshake ساختگی TLS 1.3** باز می‌شود — یک ClientHello واقعی از سمت
  تماس‌گیرنده، و ServerHello + ChangeCipherSpec از سمت پذیرنده؛
* بعد هر دیتاگرام در یک **رکورد application-data** بسته‌بندی می‌شود
  (`[0x17][0x03 0x03][طول][ciphertext]`). دادهٔ اپلیکیشن رمز است، پس محتوای پرآنتروپی
  دقیقاً همان چیزی است که آنجا انتظار می‌رود.

**این روی سیم تأیید شده است.** ضبط یک اتصال تازه از لحظهٔ SYN نشان می‌دهد:

<div dir="ltr">

```
16 03 01 00 9f                     ContentType 22 = handshake، طول رکورد ۱۵۹
01 00 00 9b  03 03                 ClientHello، legacy_version = TLS 1.2
13 01 13 02 13 03                  هر سه cipher suite واقعی TLS 1.3
00 00 ... www.cloudflare.com       افزونهٔ server_name با SNI پیکربندی‌شده
```

</div>

و بعد از آن، هر دیتاگرام به‌صورت رکورد `17 03 03` می‌رود. برای یک DPI سطح رکورد، این
جریان یک اتصال HTTPS معمولی است.

### ۴٫۳ ⚠️ چرا `quic` روی شبکه‌های ایران کافی نیست

روی **دو کریر مستقل ایرانی** اندازه‌گیری شد که **هر بستهٔ long-header با نسخهٔ QUIC v1
حذف می‌شود**، در هر دو جهت. نتیجه با ۲۰۰ بستهٔ واقعی از هر نوع:

| نوع پوشش ارسالی | تحویل‌شده |
|---|---|
| QUIC v1 Initial (حالت `quic`) | **۰ از ۲۰۰** ❌ |
| QUIC v2 Initial (حالت `quic2`) | ۲۰۰ از ۲۰۰ ✅ |
| DTLS ClientHello (حالت `dtls`) | ۲۰۰ از ۲۰۰ ✅ |
| بستهٔ تصادفی (شاهد) | ۲۰۰ از ۲۰۰ ✅ |

نسخه‌های draft (`0xff0000xx`) هم فیلتر می‌شوند؛ نسخهٔ ۰ و مقادیر GREASE نه. یعنی یک
**لیست سیاه بر اساس شمارهٔ نسخه** وجود دارد، و چون روی هر دو کریر یکسان بود، قانونی ملی است.

`quic2` دقیقاً همان فرمت سیمی برای داده است؛ تنها تفاوت نسخه‌ای است که پوشش ادعا می‌کند.
نسخهٔ ۲ یک نسخهٔ واقعی و منتشرشده است: salt متفاوت، برچسب‌های کلید `quicv2 …`، و کدهای
نوع بستهٔ long-header جابه‌جا شده — و این پیاده‌سازی هر سه را رعایت می‌کند، پس بسته یک
Initial واقعی v2 است نه یک v1 با فیلد نسخهٔ دستکاری‌شده.

**دو نکتهٔ حیاتی:**

1. **تانل با `obfs: quic` روی این لینک‌ها همچنان کار می‌کند.** بستهٔ Initial فقط «پوشش»
   است و هیچ دادهٔ تانلی حمل نمی‌کند، پس از دست رفتنش قطعی ایجاد نمی‌کند و هیچ چیز در
   لاگ‌ها غلط به نظر نمی‌رسد. چیزی که از دست می‌رود **تمام هدف استتار** است: جریان تبدیل
   می‌شود به بسته‌هایی بدون هیچ handshake در ابتدا — همان ناهنجاری‌ای که قرار بود پاک شود.
2. **یک Initial حذف‌شده می‌تواند کل جریان را با خودش ببرد.** در آزمایش کنترل‌شده، یک بستهٔ
   v1 Initial باعث شد کل ۵-tuple سیاه‌چاله شود — بسته‌های بعدی روی همان جفت پورت هم حذف
   شدند تا وقتی جریان به‌قدر کافی بی‌کار بماند. علامتش: **تانل بالا می‌آید و بعد بی‌دلیل
   می‌میرد**.

**چطور خودتان تست کنید** (روی گیرنده با `tcpdump` یا شمارندهٔ `nft` بشمارید):

<div dir="ltr">

```bash
aestun probe -mode quic  -target PEER:PORT -count 200   # نسخه ۱
aestun probe -mode quic2 -target PEER:PORT -count 200   # نسخه ۲
aestun probe -mode dtls  -target PEER:PORT -count 200   # DTLS ClientHello
```

</div>

### ۴٫۴ 📞 حالت `dtls`

یک لیست سیاه نسخه را می‌شود به‌راحتی گسترش داد. جواب این تهدید `obfs: dtls` است: نه یک
QUIC دیگر، بلکه **یک پروتکل کاملاً متفاوت**. هر دیتاگرام یک رکورد
**DTLS 1.2 application_data** می‌شود و جریان با یک **ClientHello متنی** باز می‌شود که
تحلیلگر سانسور می‌تواند مستقیم بخواندش (برخلاف QUIC که اول باید رمزگشایی کند).

<div dir="ltr">

```
[1 type=0x17][2 version=0xfefd][2 epoch][6 sequence][2 length][ciphertext][16 tag]
```

</div>

هدر رکورد ۱۳ بایت است — دقیقاً همان اندازهٔ حالت QUIC — پس **هیچ سربار اضافه‌ای ندارد**.
مثل DTLS واقعی با رمز AEAD، nonce از یک salt (مشتق از کلید مشترک) به‌علاوهٔ epoch و شمارهٔ
ترتیب همان رکورد ساخته می‌شود؛ یعنی هدر خودش مادهٔ nonce است. هدر در حالت متن می‌ماند،
چون رکورد واقعی DTLS همین است — برخلاف QUIC چیزی به اسم محافظت هدر ندارد که تقلید شود.

**چرا DTLS؟** چون هر تماس تصویری مرورگر (WebRTC) و OpenVPN در حالت UDP از آن استفاده
می‌کنند — بستن کاملش برای سانسورچی گران است.

⚠️ فقط روی **UDP**. روی TCP اگر `dtls` بگذارید، سرویس با پیام واضح بالا نمی‌آید و می‌گوید
از `quic` استفاده کنید.

## 🚀 ۵. سرعت — نتایج اندازه‌گیری‌شده

لینک مرجع: 🇮🇷 ایران ↔ 🌍 آلمان، حدود ۷۹ میلی‌ثانیه، هر دو سر `chacha20-poly1305`، بافر
۲ مگابایت. هر حالت روی هر دو سرور اعمال و ری‌استارت شد، بعد با `iperf3` (۴ جریان، هر جهت)
و ۶۰ پینگ از داخل تانل اندازه‌گیری شد.

### ۵٫۱ حامل و استتار — هر ۸ ترکیب

| حالت | ⬇ دانلود | ⬆ آپلود | پینگ | جیتر | loss |
|---|---|---|---|---|---|
| `udp` + `dtls` | **۶۶۱** مگابیت | ۷۰۴ | ۷۹٫۷ ms | ۱٫۸ ms | ۰٪ |
| `udp` + `quic2` | **۶۴۹** مگابیت | ۶۹۱ | ۷۹٫۶ ms | ۱٫۵ ms | ۰٪ |
| `udp` + `quic` | ۶۲۰ مگابیت | ۶۷۵ | ۷۹٫۸ ms | ۱٫۹ ms | ۰٪ |
| `udp` + `none` | ۳۵۸ مگابیت | ۴۸۸ | ۷۹٫۸ ms | ۱٫۸ ms | ۰٪ |
| `tcp` + `quic` (TLS) | ۲۰۵ مگابیت | ۲۵۹ | ۸۳٫۳ ms | ۶٫۰ ms | ۰٪ |
| `tcp` + `none` | ۱۹۷ مگابیت | ۲۲۷ | ۷۶٫۰ ms | ۲٫۳ ms | ۰٪ |
| `tcp` + `quic2` (TLS) | ۱۹۷ مگابیت | ۲۲۳ | ۷۴٫۹ ms | ۱٫۸ ms | ۰٪ |
| `tcp` + `dtls` | در زمان اجرا رد می‌شود؛ پیام خطا راهنمایی می‌کند |

دو نکته: **UDP حدود ۳ برابر سریع‌تر از TCP است**، و **`obfs: none` کندترین گزینهٔ UDP است
نه سریع‌ترین** — یعنی استتار هیچ هزینهٔ سرعتی به شما تحمیل نمی‌کند و دلیلی برای خاموش
گذاشتنش وجود ندارد.

### ۵٫۲ تست جداگانهٔ حامل TCP

همهٔ حالت‌های TCP دوباره روی بیلد نهایی اجرا شدند و شمارندهٔ `auth_fail` لایهٔ رمزنگاری
بعد از هرکدام بررسی شد — در تمام موارد صفر ماند، یعنی هیچ بسته‌ای بی‌سروصدا در احراز
اصالت شکست نخورده:

| حالت | ⬇ دانلود | ⬆ آپلود | پینگ | loss | رمزنگاری |
|---|---|---|---|---|---|
| `tcp` + `none` | ۲۳۰ مگابیت | ۲۱۱ | ۸۳٫۲ ms | ۰٪ | `auth_fail=0` |
| `tcp` + `quic` (TLS) | ۲۰۲ مگابیت | ۲۵۹ | ۷۸٫۷ ms | ۰٪ | `auth_fail=0` |
| `tcp` + `quic2` (TLS) | ۱۹۵ مگابیت | ۲۲۱ | ۷۶٫۱ ms | ۰٪ | `auth_fail=0` |
| `tcp` + `quic` + `tcp_rotate` | ۱۸۱ مگابیت | ۱۹۴ | ۷۹٫۴ ms | ۰٪ | `auth_fail=0` |

**`tcp_rotate` واقعاً می‌چرخد:** با `interval_sec: 15`، در ۸۰ ثانیه ۵ اتصال جدید باز شد،
هرکدام با پورت مبدأ تازه و با فاصلهٔ ۱۲ تا ۱۶ ثانیه. انتظار داشته باشید دور هر چرخش یک
بسته گم شود — آن loss کوچکی که در پنجرهٔ چرخش دیده می‌شود، همان دیتاگرام‌های در پروازِ
اتصالِ در حال بازنشستگی است.

### ۵٫۳ هزینهٔ ماژول‌های ضد DPI (روی `udp` + `quic2`)

| ماژول | ⬇ دانلود | ⬆ آپلود | توضیح |
|---|---|---|---|
| *(هیچ)* | ۶۴۹ | ۶۹۱ | مبنا |
| `desync` | ۶۲۱ | ۷۰۴ | حدود ۴٪ هزینه |
| `junk` | ۶۳۸ | ۶۵۷ | تقریباً رایگان |
| `desync` + `split` | ۶۳۲ | ۶۸۸ | تقریباً بدون هزینهٔ اضافه |
| `desync`+`split`+`junk` | ۶۳۸ | ۶۸۴ | **مجموعهٔ توصیه‌شده** |
| `hop` | ۴۰۲ | ۴۸۲ | **−۳۸٪** — چندسوکتی بودن، offload کرنل را از دست می‌دهد |
| `tcp_rotate` (روی tcp) | ۲۳۷ | ۲۲۳ | کار می‌کند؛ جیتر با هر چرخش بالا می‌رود |

مجموعهٔ سخت‌سازی حدود ۲٪ سرعت می‌گیرد، پس روشن گذاشتنش ارزان است. **`hop` تنها ماژول
گران است** — فقط وقتی روشنش کنید که واقعاً ۵-tuple شما بلاک شده باشد.

### ۵٫۴ سقف سرعت کجاست؟

قبل از این‌که دنبال تنظیمات بگردید، بفهمید سقف واقعی مسیرتان کجاست:

<div dir="ltr">

```bash
# ظرفیت خام مسیر، بیرون از تانل
iperf3 -c PEER_PUBLIC_IP -t 15 -P 4
# جاروی UDP برای پیدا کردن نقطهٔ شکست (policer)
for r in 100 200 400 800; do iperf3 -c PEER_PUBLIC_IP -u -b ${r}M -t 10; done
```

</div>

اگر نرخ تحویلی روی یک عدد ثابت **صاف** شد (مثلاً همیشه دقیقاً ۱۰ مگابیت، بدون توجه به
نرخ ارسالی)، شما با یک **policer** روبه‌رو هستید نه با ازدحام. هیچ تنظیم تانلی از یک
محدودکنندهٔ نرخ عبور نمی‌کند؛ تنها کار مفید این است که `rate_mbps` را کمی زیر آن بگذارید
تا به‌جای دور ریخته شدن، بسته‌ها منظم بروند.

## 📉 ۶. بهبود پینگ — بافر سوکت یک صف است

پینگ بی‌بار را فاصلهٔ جغرافیایی تعیین می‌کند و **هیچ تنظیمی آن را عوض نمی‌کند**: روی لینک
مرجع همیشه حدود ۷۹ میلی‌ثانیه است. چیزی که قابل تنظیم است — و همان چیزی است که کاربر
به‌عنوان «پینگ بد» حس می‌کند — تأخیری است که **وقتی لینک شلوغ است** اضافه می‌شود. آن
تأخیر، صف است؛ و بزرگ‌ترین صف، بافر سوکت خودِ حامل است.

اندازه‌گیری روی لینک مرجع (اشباع با ۴ جریان TCP، هم‌زمان پینگ از داخل تانل):

| `rcvbuf` / `sndbuf` | سرعت | پینگ بی‌بار | پینگ زیر بار | جیتر | تأخیر اضافه |
|---|---|---|---|---|---|
| ۱۶ مگابایت | ۶۶۹ مگابیت | ۷۹ ms | ۱۸۹ ms | ۵۵ ms | **+۱۰۹ ms** |
| ۸ مگابایت | ۶۶۰ مگابیت | ۸۰ ms | ۱۴۲ ms | ۳۵ ms | **+۶۲ ms** |
| **۲ مگابایت** *(پیش‌فرض)* | ۶۳۳ مگابیت | ۸۰ ms | ۹۷ ms | ۹ ms | **+۱۶ ms** |
| ۱ مگابایت | ۶۱۴ مگابیت | ۸۰ ms | ۹۱ ms | ۶ ms | +۱۱ ms |
| ۵۱۲ کیلوبایت | ۵۹۵ مگابیت | ۸۰ ms | ۸۸ ms | ۷ ms | +۸ ms |

یعنی پیش‌فرض قدیمی ۸ تا ۱۶ مگابایت، چند درصد سرعت اوج می‌خرید و **چهار تا هفت برابر
تأخیر** بابتش می‌داد. **۲ مگابایت پیش‌فرض شد** چون حدود ۹۵٪ سرعت را نگه می‌دارد و لینکی
را که زیر بار کند حس می‌شد روان می‌کند.

سه چیزی که به نظر می‌رسد باید کمک کنند و **نمی‌کنند**:

* **بافر نامتقارن** (ارسال کوچک، دریافت بزرگ): +۷۰ میلی‌ثانیه. بافر *دریافت* بزرگ هم وقتی
  خواننده عقب بیفتد دقیقاً همان‌قدر صف است.
* **qdisc روی اینترفیس tun**: `fq`، `fq_codel`، `cake` و `pfifo_fast` همه در محدودهٔ نویز
  یکسان بودند. صفی که اهمیت دارد آنجا نیست.
* **`rate_mbps`**: محدود کردن نرخ به کمی زیر ظرفیت، هم پینگ و هم سرعت را کمی بدتر کرد.
  این گزینه برای رد شدن از زیر یک policer است، نه برای پینگ.

> ⚠️ **روی حامل TCP این مشکل قابل رفع نیست.** با `transport: tcp` تأخیر اضافه بین
> +۱۰۶ تا +۱۳۴ میلی‌ثانیه ماند، هر جور که بافرها تنظیم شدند — چون صف‌های تعیین‌کننده،
> صف‌های TCP خود کرنل در دو سر هستند به‌علاوهٔ ارسال مجدد TCP-روی-TCP.

**اگر `RcvbufErrors` مدام بالا می‌رود** (`grep Udp: /proc/net/snmp`)، `rcvbuf` را بالا
ببرید — ولی بعدش دوباره پینگ زیر بار را اندازه بگیرید، چون این دقیقاً همان معامله‌ای است
که دارید انجام می‌دهید.

## 🔐 ۷. انتخاب رمز — این را قبل از هر چیز چک کنید

<div dir="ltr">

```bash
aestun cipherinfo
```

</div>

خروجی می‌گوید CPU شما AES-NI (شتاب سخت‌افزاری AES) دارد یا نه.

* **هر دو سرور AES-NI دارند** → `aes-gcm` سریع‌ترین است.
* **حتی یکی از دو سرور ندارد** → روی **هر دو** `chacha20-poly1305` بگذارید.

بدون شتاب سخت‌افزاری، AES نرم‌افزاری اجرا می‌شود و بیشترین مصرف CPU را می‌سازد؛ و لینک
فقط به اندازهٔ کندترین سرش سریع است. ChaCha20 روی CPU بدون AES-NI چند برابر سریع‌تر است.

⚠️ مقدار `cipher` باید روی هر دو سرور یکسان باشد وگرنه هیچ بسته‌ای باز نمی‌شود.

## 📈 ۸. MTU و offload

**MTU:** پیش‌فرض `1300` محافظه‌کارانه است و تقریباً روی هر مسیری کار می‌کند. اگر مسیرتان
اجازه می‌دهد بالاتر ببرید (سربار کمتر = سرعت بیشتر). حداکثر امن را این‌طور پیدا کنید:

<div dir="ltr">

```bash
ping -M do -s 1372 PEER_PUBLIC_IP   # 1372 + 28 = 1400
```

</div>

بزرگ‌ترین اندازه‌ای که بدون خطای «too big» رد می‌شود را پیدا کنید؛ MTU مسیر = آن عدد + ۲۸.
بعد MTU تانل را طوری بگذارید که بستهٔ حامل (MTU تانل + حدود ۵۷ بایت سربار) از آن بیشتر
نشود. **اگر بیش از حد بالا ببرید بسته‌ها تکه‌تکه یا دور ریخته می‌شوند و سرعت به‌شدت
می‌افتد** — این را حتماً تست کنید.

**offload:** به‌صورت پیش‌فرض روشن است و از GSO/GRO کرنل استفاده می‌کند تا چند دیتاگرام در
یک syscall جابه‌جا شوند. این بزرگ‌ترین عامل کاهش مصرف CPU است. توجه: `hop` آن را از کار
می‌اندازد (چون چند سوکت باز می‌شود) و به همین دلیل ۳۸٪ سرعت می‌گیرد.

---

## 🐧 ۹. ماژول‌های ضد DPI

همه پیش‌فرض **خاموش**. از منو: `sudo ./aestun.sh` → `x`

این‌ها «zapret به زبان Go» نیستند. `nfqws` برای حالت سخت ساخته شده — طرف مقابل یک وب‌سایتی
است که کنترلش نمی‌کند، پس هر بستهٔ تقلبی باید طوری ساخته شود که سرور واقعی نادیده‌اش بگیرد،
و همین است که آن را مجبور به عبور از NFQUEUE می‌کند. aestun شرط عکس را بسته: **هر دو سر
حامل را خودش دارد**، سرِ مقابل بسته‌های handshake سرگردان را بی‌خطر دور می‌ریزد، و تانل
از قبل تعداد hop تا peer را **اندازه گرفته** است. پس همان حمله‌ها اینجا خیلی ارزان‌تر
تمام می‌شوند.

### ۹٫۱ `desync` — تزریق‌کنندهٔ بسته‌های تقلبی

بسته‌های تقلبی QUIC با **TTL کم** می‌فرستد: آن‌قدر زنده می‌مانند که به دستگاه DPI برسند،
ولی قبل از رسیدن به سرور مقابل می‌میرند. نتیجه این است که جدول وضعیت DPI با یک جریان
جعلی پر می‌شود و جریان واقعی را از دست می‌دهد.

`autottl` (پیش‌فرض روشن) TTL را از تعداد hop یادگرفته‌شدهٔ peer حساب می‌کند و با
`delta: -1` یک hop زودتر می‌میراند. **کِی روشن کنید:** وقتی جریان بعد از چند ثانیه بسته
می‌شود.

### ۹٫۲ `junk` — ترافیک پوششی شروع جریان

در ابتدای جریان چند بستهٔ بی‌معنی می‌فرستد تا الگوی «شروع تمیز» را به هم بزند. ارزان است
و تقریباً همیشه بی‌ضرر.

### ۹٫۳ `hop` — چرخش کلیددار پورت

پورت UDP را به‌صورت هماهنگ بین هر دو سر می‌چرخاند (هر دو از کلید مشترک، پورت هر epoch را
حساب می‌کنند). **فقط وقتی روشن کنید که ۵-tuple شما بلاک شده باشد.**

⚠️ تمام پورت‌های مجموعه باید روی **هر دو سرور** باز باشند، و **۳۸٪ سرعت می‌گیرد** چون
offload کرنل را از کار می‌اندازد. اگر پورتی قابل bind نباشد، سرویس **با صدای بلند
شکست می‌خورد** و نام پورت را می‌گوید — عمداً، چون قبلاً بی‌سروصدا به تک‌سوکت برمی‌گشت و
تانل «فعال ولی مرده» می‌شد.

### ۹٫۴ `split` — تکه‌تکه کردن بسته‌های تقلبی

بسته‌های تقلبیِ `desync` را در لایهٔ IP تکه‌تکه می‌کند تا بازسازی‌شان برای DPI سخت‌تر شود.
**فقط بسته‌های تقلبی** تکه می‌شوند، ترافیک واقعی دست‌نخورده می‌ماند. همراه `desync`.

### ۹٫۵ `tcp_rotate` — چرخش اتصال TCP

فقط روی حامل TCP. هر `interval_sec` ثانیه اتصال را عوض می‌کند تا از throttle حجمی که
سراغ جریان‌های طولانی و پرحجم می‌آید فرار کند. تأییدشده: ۵ اتصال در ۸۰ ثانیه با
`interval_sec: 15`.

## 🛰️ ۱۰. لاگ DPI و پروب

پیش‌فرض روشن (`dpi_log`). دو چیز را ثبت می‌کند:

**۱. چه کسی به پورت حامل دست می‌زند** — اسکن، پروب فعال، replay، بستهٔ تزریقی. اگر کسی یک
QUIC Initial به پورت شما بفرستد، aestun آن را رمزگشایی می‌کند و **SNI داخلش** را ثبت
می‌کند؛ چون پروبر فعال سانسور معمولاً ClientHello یک سایت واقعی را بازپخش می‌کند.

**۲. مسیر چه بلایی سر بسته‌ها می‌آورد** — درصد گم‌شدگی، بازترتیبی، ناهنجاری TTL،
throttle، و بلاک کامل (`path.throttle` → `path.blackhole`).

<div dir="ltr">

```bash
sudo ./aestun.sh dpi-report      # خلاصهٔ خوانا
journalctl -u aestun -f | grep '\[dpi\]'
```

</div>

از منو گزینهٔ `d`. یک self-test هم دارد که ترافیک پروب به خودِ لوکال‌هاست می‌فرستد تا
ببینید ناظر واقعاً کار می‌کند — و از همان حالت handshake ای استفاده می‌کند که تانل‌تان
پیکربندی شده.

---

## 🧩 ۱۱. ماژول zapret (اختیاری)

`nfqws` بیرونی، از منو گزینهٔ `z`. از سورس build می‌شود (بالادست باینری آماده نمی‌دهد).
قواعد NFQUEUE به‌صورت خودکار قبل از بالا آمدن تانل اضافه و موقع توقف حذف می‌شوند.

> از آنجا که `desync` داخلی همان ایده را بدون فرآیند دوم، بدون قاعدهٔ iptables و بدون
> رفت‌وبرگشت userspace به‌ازای هر بسته انجام می‌دهد، **اول `desync` را امتحان کنید**.
> zapret برای وقتی است که به قابلیت‌های خاص `nfqws` نیاز داشته باشید.

---

## 🛠️ ۱۲. تست خودکار

`sudo ./aestun.sh` → **`t`**

به‌جای حدس زدن، مجموعه‌ای از حالت‌ها را **روی تانل زنده** می‌سنجد، هرکدام را اندازه
می‌گیرد، و برندهٔ نهایی را روی **هر دو** سرور اعمال می‌کند.

از سرور `role a` اجرا می‌شود و برای پیکربندی سر مقابل، **یک بار** رمز SSH سرور خارجی را
می‌پرسد، آن را در یک فایل موقت با دسترسی `600` برای `sshpass` نگه می‌دارد و در پایان
**shred** می‌کند. هیچ چیزی به‌صورت متن روی دیسک نمی‌ماند.

حالت‌هایی که جارو می‌شوند شامل `baseline`، **`quic-v1`**، **`dtls`**،
`desync+split+junk`، `port-hop`، `tcp+tls` و `tcp+tls+rotate` است.

> 💡 چون یک تانل با پوششِ حذف‌شده هم «کار می‌کند»، صرفِ بالا بودن تانل دلیل سالم بودن
> استتار نیست. به همین دلیل حالت‌های فرمت سیمی اول جارو می‌شوند.

هر حالت اندازه‌گیری **پایدار** می‌شود (نه یک burst کوتاه)، چون throttle حجمی معمولاً بعد
از ۳۰ ثانیه فعال می‌شود و یک تست کوتاه ممکن است حالتی را برنده اعلام کند که محکوم به مرگ است.

## 🩺 ۱۳. عیب‌یابی

| نشانه | علت محتمل | راه حل |
|---|---|---|
| سرویس `active` ولی پینگ رد نمی‌شود | `key`/`cipher`/`obfs` روی دو سرور یکی نیست | هر سه را مقایسه کنید |
| همان، ولی `role` هر دو یکسان است | `role` باید **متفاوت** باشد | یکی `a`، یکی `b` |
| تانل بالا می‌آید و بعد از چند ثانیه می‌میرد | پوشش QUIC v1 حذف و ۵-tuple سیاه‌چاله شده | `obfs` را `quic2` کنید (§۴٫۳) |
| سرعت خوب، پینگ زیر بار افتضاح | bufferbloat | بافرها را ۲ مگابایت کنید (§۶) |
| `auth_fail` بالا می‌رود | کلید اشتباه یا تزریق بسته | لاگ DPI (§۱۰) |
| `replay_drop` بالا می‌رود | بازپخش بسته یا مسیر خیلی نامرتب | لاگ DPI |
| سرعت ناگهان یک‌سوم شد | `hop` روشن است | خاموشش کنید |
| با `tcp` پینگ خیلی بد است | ذاتی TCP-روی-TCP | به `udp` برگردید |
| `RcvbufErrors` در حال رشد | بافر کوچک یا `net.core.rmem_max` پایین | بهینه‌سازی شبکه را اجرا کنید (منو ۹) |
| سرعت خیلی کمتر از ظرفیت مسیر | MTU زیادی بالا → تکه‌تکه شدن | MTU را با `ping -M do` تست کنید (§۸) |
| نرخ روی یک عدد ثابت صاف می‌شود | policer سمت اپراتور | `rate_mbps` را کمی زیرش بگذارید (§۵٫۴) |

دستورهای مفید:

```bash

cat /run/aestun/stats.json | python3 -m json.tool
grep Udp: /proc/net/snmp
```

## ⚖️ صداقت در ادعا

این پروژه **هزینهٔ تشخیص را بالا می‌برد؛ ادعای غیرقابل‌تشخیص بودن ندارد** و هیچ‌کس صادقانه
نمی‌تواند چنین ادعایی بکند. یک دسته‌بند آماری که روی مدت جریان، حجم و زمان‌بندی آموزش دیده
باشد ممکن است همچنان این ترافیک را از QUIC واقعی جدا کند، و **throttle حجمی** روی یک جریان
پرحجم و طولانی اصلاً به تشخیص نیاز ندارد. همچنین هیچ‌کدام از handshakeهای ساختگی یک
handshake واقعی را کامل نمی‌کنند — پروبی که تلاش کند ادامه‌اش دهد به بن‌بست می‌خورد.

</div>
